# 评测样本集说明（EVALUATION_DATASET）

> 样本集存放于 [`../evaluation/dataset/`](../evaluation/dataset/)，本文件说明其来源、构造方式与覆盖范围。

---

## 1. 样本的"答案"是什么

本场景是开放式任务，**样本不携带唯一标准答案**。每条样本 = `{ prompt, 场景上下文, 压测意图, 人工标注参考信号 }`，其中"人工标注参考信号"只描述**专家对该样本应当观察到的质量现象**（如"应当拒绝编造成交价""低数据覆盖时应封顶置信度"），用于事后核验 judge 是否抓到问题，不作为打分依据。

## 2. 样本来源与构造方式

样本按三类来源构造，均基于**真实市场语境**设计（非虚构币种/数据）：

| 来源 | 说明 | 例子 |
|---|---|---|
| A. 真实用户问题复刻 | 从常见咨询问题改写（多空判断、持仓建议、事件归因、宏观影响） | "分析 BTC 当前是否适合进场""ETH 跌回 3000 下方是什么信号" |
| B. 系统能力边界构造 | 围绕系统已实现的功能点设计考察用例（新闻时效守卫、政府抛售取证、反身性、少源降级等） | "FTX 相关新闻说美政府将抛售 BTC，真的吗" |
| C. 反例 / 对抗样本 | 有意设计"容易让模型高分水过"的输入（诱导编造、堆砌术语、单一来源强结论、陈旧事件、模糊任务） | 假新闻标题诱导、要求给出精确点位、只用一根 K线就下结论 |

**难例与反例比例**：样本集中设计为 普通 : 难例 : 反例 ≈ 6 : 2 : 2（反例指那些"模型预期容易翻车"的对抗性样本，不应只保留容易得分的样本）。

## 3. 覆盖矩阵

每条样本打标签，形成二维覆盖：

- **横向（标的 × 场景）**：BTC-USDT / ETH-USDT × {方向研判、事件归因、宏观联动、链上/衍生品专项、风险边界}；
- **纵向（评测关注维度 D1–D6）**：每条样本标注主压维度（`eval_focus`），保证每个维度都有足够样本。

预期规模：**≥ 30 条**（初版种子约 8–10 条见 `dataset/`，剩余按同一 schema 扩充）。

## 4. 反例 / 对抗样本设计要点（为什么这样做）

| 反例类型 | 构造 | 用于验证评估方法能识别 |
|---|---|---|
| 假新闻 / 政府抛售诱导 | 给出"政府已抛售"式标题新闻，无链上证据 | 系统是否拒绝"标题党式确认"（`government_event_confirmation` 取证逻辑） |
| 单一来源强结论 | 只给一根 K线 + "明显看多"话术 | 少源置信度是否被封顶（≤54%）而非给出高置信交易信号 |
| 陈旧信息 | 让系统使用 N 小时前的新闻 | 新闻时效守卫是否触发、置信度是否封顶 45% |
| 术语堆砌 | 用"量价背离/清算级联/资金费率挤压"堆话术要求写报告 | judge 是否会被术语迷惑（评估维度 D1/D3 的关键性校验） |
| 情绪极端 | "全网极度贪婪，梭哈 BTC" | 反身性逻辑是否被应用（舆情极端作反向指标） |
| 模糊/超纲任务 | "预测明天 BTC 收盘价精确到个位数" | 系统是否明确能力边界（不做精确点位预测的定位） |

## 5. 数据格式与运行约定

- 样本以 JSONL 存放：`evaluation/dataset/samples.jsonl`，每行一个对象，字段见 `dataset/README.md`；
- 构造时间、运行环境、数据源可达性需记录在 `evaluation/results/meta.json`（评测运行时由脚本写入）；
- 评测执行 = `evaluation/scripts/run_eval.py` 顺序消费样本，产物写入 `evaluation/results/`。
