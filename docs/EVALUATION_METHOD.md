# 评估方法设计说明（EVALUATION_METHOD）

> 对应实战任务：**任务一 · 开放式场景：AI 应用与评判标准设计**
> 应用：CryptoSage（Hy3 加密货币研判多 Agent 系统）
> 场景产出：面向用户问题的**多步分析与研判报告**（过程事件流 + 结构化研判 JSON + 可读报告）

---

## 1. 为什么要自定义评估方法

本场景（"分析 BTC/ETH 当前是否值得进场 / 发生了什么 / 后续怎么看"）的输出：

- 没有唯一标准答案：不同时点的正确结论不同，且"正确"取决于时效；
- 产出是**多步骤的复合产物**：包含数据采集 → 分维度研判 → 融合 → 对抗审查 → 报告；
- 用户真正关心的是**过程是否可靠、结论是否可追溯、风险是否说清**，而非一个孤立的点位数字。

因此通用 benchmark（如单轮 QA 正确率）无法胜任，需要针对本场景的产出物定义一套**分维度、可操作、可自动执行**的评估方法。

**评估对象**：系统在一次分析任务中产出的"研判报告 + 过程留痕"，判定其作为一份"研究分析产物"的质量。评估器不直接评价价格预测对错（那是影子回测/校准体系负责的另⼀条线），而是评价**分析产物本身是否值得被信任**。

---

## 2. 评估维度（5 + 1）

每个维度配**行为锚定标准**（`evaluation/rubric.md` 中有 1–5 分的逐档描述），评审者按可观察证据打分，同一份输出由不同评审者打分应趋于一致。

| 维度 | 名称 | 评估的问题 | 可观察判定要点 |
|---|---|---|---|
| D1 | 事实与数据准确性 | 报告引用的数值、事件、指标是否真实存在且与输入证据一致？ | 抽查 K线/指标/费率/OI/爆仓/新闻事件等断言；核对证据池与工具返回值；是否有**编造数据或断章取义** |
| D2 | 证据可追溯性 | 每条关键结论能否回指到具体来源？ | 方向判断是否由 `evidence_pool` 中可定位的信号支撑；关键价位是否带 confluence 与算法依据；风险陈述是否说明依据 |
| D3 | 推理与融合一致性 | 多源证据是否被正确对待？结论与证据是否自洽？ | 方向是否与加权一致度匹配；是否存在"证据不足却高置信"；市场状态与权重档位是否合理；Critic 质疑是否被有效回应 |
| D4 | 风险与合规表达 | 是否充分、合规地表达不确定性？ | 是否给出风险边界/失效条件/尾部风险（`black_swan_risks`）；是否带免责声明；低置信时是否降级为观望而非交易建议 |
| D5 | 结构化与格式规范 | 输出是否可作为结构化产物消费？ | 报告 JSON schema 字段完整性、类型正确性、关键字段缺失情况；报告可读性 |
| D6（+1，过程维度） | 过程效率与稳定性 | 单任务执行是否收敛、无空转/死循环？ | 调用步数、超时/错误、Critic 收敛、任务是否按时产出终态 |

> D6 为本场景自定义的**过程质量**维度：开放场景的多 Agent 系统"答不出来还硬答 / 空转烧步数"是常见失败模式，应纳入评估。

## 3. 判定标准的可操作性设计

避免"较好地满足 / 基本符合"式表述，全部使用**证据性锚点**。示例（完整版见 `evaluation/rubric.md`）：

- D1·3 分锚点："报告所有数值断言均可从证据池或工具返回值中定位，抽查 5 处无错误；允许 1 处表述歧义。"
- D1·1 分锚点："出现 ≥1 处与证据矛盾的数值或事件（编造/张冠李戴）。"
- D2·5 分锚点："每个方向性结论至少可回指 2 个独立维度信号，关键价位可回指算法 confluence 来源。"

评审流程：先做**规则校验**（字段完整性、disclaimer 存在、execution_mode 与 confidence 一致性、重复文本检测等，输出硬性 0/1 项），再进入**逐维度打分**。

---

## 4. 评分方式：LLM-as-judge + 规则校验（含设计依据）

### 4.1 为什么选 LLM-as-judge + 规则校验

- **规则校验**：报告是结构化 JSON，schema/字段/一致性等维度的很大一部分可用确定性规则自动判定，成本低且 100% 可复现；
- **LLM-as-judge**：D1–D5 中"是否编造、是否可追溯、推理是否自洽"是语言质量判断，规则无法覆盖，需模型按 rubric 打分；
- **为什么用 Hy3 当 judge**：与受评系统同一模型会引入同源偏差，因此默认采用**双 judge + 仲裁**：judge 使用 Hy3（生产同款）与可配置的对照模型（默认 DeepSeek）各打一遍，分歧过大时由 Hy3 慢思考做最终仲裁。这一设计是为了检验评估方法自身的稳定性（一致性验证见 `VALIDATION.md`）。

### 4.2 单样本评测流水线

```
样本 prompt
   │
   ▼
[1] 运行应用：POST /api/analyze → 轮询 /api/report/{id}
   │   产物：evidence_pool + synthesis_result(final report) + execution_trace
   ▼
[2] 规则校验（确定性）→ hard 指标（schema/字段/一致性/重复）
   ▼
[3] 两路 LLM-as-judge（rubric 逐维度 1-5）
   ▼
[4] 分歧仲裁（>1 分分歧 → Hy3 慢思考复审）
   ▼
[5] 汇总：维度得分 + 总分 + 失败模式标签（见 §6）
```

评测脚本见 `evaluation/scripts/`；一次运行输出到 `evaluation/results/` 与 `docs/EVALUATION_RESULTS.md` 对应的表格。

## 5. 样本与判定的质量控制

- 每条样本除 prompt 外附带 `eval_focus`（本次重点压测哪个维度）、`expected_quality_signals`（专家预期会观察到的现象，用于事后核对 judge 是否抓到问题），见 `evaluation/dataset/`；
- 难例/反例比例与覆盖矩阵见 `EVALUATION_DATASET.md`；
- 人工抽检：LLM-as-judge 结果抽样做人工复核，作为一致性验证的一部分（见 `VALIDATION.md`）。

## 6. 失败模式标签体系（供归因与后续分析报告使用）

| 标签 | 含义 | 典型观测信号 |
|---|---|---|
| `hallucinated_fact` | 编造/与证据冲突的数值或事件 | 报告中价格/事件与证据池不符 |
| `untraceable_claim` | 关键结论无法回指证据 | 方向结论无信号支撑、无 confluence |
| `overconfident` | 证据不足但置信度高 | 单源方向源却高置信（应被 ≤54%/≤35% 封顶） |
| `stale_news` | 使用了滞后/失效信息 | 新闻抓取滞后但未被守卫拦截 |
| `fake_consensus` | 看似多源一致实则被单源主导 | 实际只 1 个方向源 |
| `compliance_miss` | 合规/免责/风险缺失 | 无 disclaimer、低置信却给仓位建议 |
| `empty_flail` | 空转/未收敛/产出质量差 | 大量步骤无新证据、重复内容、字段缺失 |
| `schema_error` | 结构化输出不达标 | JSON 字段缺失/类型错误 |
| `format_issue` | 可读性差 | 列表被对象污染、渲染异常文本 |

> 以上标签会随评测运行不断补充（在 `ANALYSIS_REPORT.md` 的"实测典型模式"中记录真实样例），此处为初版体系，用于指导评测与归因。

---

## 7. 与"方向对错"评估（影子回测校准）的分工

- 本评估方法评价**分析产物质量**（信任度）；
- 方向对错由系统内置的**影子回测**以确定性方式评估：每次方向性研判进入影子追踪，24h 固定窗口结算，统计准确率/Brier/盈亏，并反哺 Agent 动态权重（`backend/calibration/performance.py`，`/api/shadow/stats` 可查）。
- 两者共同回答"这个系统值不值得信任"，前者回答"说得对不对"，后者回答"过程/表达靠不靠谱"，在 `ANALYSIS_REPORT.md` 中汇总。
